The complete guide

Why client-side image compression wins

Most "free" image compressors on the web have a hidden cost. Here's what you're actually paying.

Where your photos go

Open any online image compressor. Drop in a photo. Watch the network tab. Your image just got uploaded to a stranger's server, processed there, sent back. For vacation pics, that's fine. For client work, unreleased product shots, medical images, anything under NDA, it's a leak waiting to happen.

This tool uses the HTML5 Canvas API. Your image never leaves the tab. The privacy badge at the top of the page is a real counter, not a slogan.

How Canvas compression works

When you load an image into a <canvas> element and call canvas.toBlob(), the browser's built-in encoder does the compression. Same encoder Chrome uses to save images, same one Firefox ships with. You get quality that matches the rest of the web, with zero server.

The quality parameter (0 to 1) controls the lossy compression ratio. Higher means bigger files, better quality. 0.8 is the sweet spot for photos.

WebP is almost always smaller

WebP is Google's image format from 2010. Most browsers support it now, and at equivalent quality, WebP files run 25-35% smaller than JPG and 80%+ smaller than PNG for screenshots. If your audience uses modern browsers (95% do), WebP is the default choice.

Pick "WebP" in the output format dropdown. You'll get the same image at a fraction of the size.

Why batch matters

If you're optimizing a blog post with 20 images, doing them one at a time on a server tool takes 4-6 minutes. Same job here: drop 20 images, the tool processes them in parallel, you download them all as a ZIP. Under 30 seconds.

The 50-file limit isn't a hard ceiling. It's the practical limit for keeping the UI snappy. If you need more, clear the queue and run another batch.

Resizing while you compress

Most "compress to under 500KB" tasks are really "this image is 4000px wide and I need it under 2000px." Compressing alone won't hit that target. Setting a max width forces the image to scale down, then compress. Same visual quality, much smaller file.

The "Max width" field in the controls bar handles this. Leave it blank to keep the original size.

When to use which format

JPG for photos with lots of color variation. PNG for screenshots, line art, anything with sharp edges and few colors (logos, UI mockups). WebP for everything modern browsers will see. The tool picks the right output automatically, but you can override.

Rule of thumb: if the source is a photo, WebP. If it's a screenshot, WebP at lossless. If you need maximum compatibility, stick with JPG.

FAQ

Common questions

Does this upload my images?

No. Every image stays in your browser tab. Compression runs on the Canvas API in your browser. Open DevTools, watch the Network tab while you compress. Zero outbound requests.

What formats work?

Input: JPG, PNG, WebP, GIF (first frame only), BMP. Output: JPG, PNG, or WebP. Most modern browsers also accept HEIC input now, but coverage is spotty.

How much can I shrink an image?

Depends on the source. A 5MB JPG photo at 80% quality usually lands around 800KB-1.2MB. PNG screenshots converted to WebP often hit 80-90% reduction. The tool shows exact savings per file.

Can I resize images too?

Yes. Set "Max width" in the controls. The image scales down proportionally, then compresses. Leave it blank to keep the original dimensions.

How many images can I process at once?

Up to 50. They process in parallel, so 50 images takes about the same time as 5. After 50, clear the queue and run another batch.

Is this better than TinyPNG or Squoosh?

Different tradeoffs. TinyPNG uses smart quantization (great PNG compression, JPG is meh) and uploads your images. Squoosh is offline-capable but single-file at a time. This tool does batch, stays offline, supports WebP conversion, and gives you a ZIP download at the end.
